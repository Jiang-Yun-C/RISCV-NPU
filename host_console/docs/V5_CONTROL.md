# NexusRV 展示台 v5 · 响应优化与四灯选择源码候选

本版在原 Windows 展示台 v4 上修改交互、计时和明确目标的多灯控制，兼容原单灯固件以及本轮新四灯固件。提供源码，**本包没有新构建的 Windows EXE，也没有新增实板速度成绩**。

## 现场使用

1. 保持板卡当前运行配置与模型装载状态，关闭占用同一串口的旧展示台或串口助手。
2. 在 Windows 安装 Python 与依赖：`py -3 -m pip install -r requirements.txt`，随后运行 `start_windows.bat`。也可用 `py -3 server.py --open` 启动浏览器版。
3. 默认地址为 `http://localhost:8766`。点击“连接板卡”选择已确认的 CP2102，打开后点击“同步 READY”。启动和打开串口均不会自动发送模型或灯控请求。
4. 演示即时灯控时，选择顶部“直接控灯”，勾选目标灯，再点“选中灯开”“选中灯关”或“读取状态”。新四灯能力确认后也可对所选灯“恢复自动指示”。默认只勾选 LED0，未选灯保持原状态；命令明确标记为直接控制，不经过模型推理。旧固件只开放 LED0，其余选项禁用。
5. 演示模型语义时，选择“模型灯控”并明确勾选目标，模型仅判断这些目标统一开还是关；普通对话不要求选灯。输入原文并发送。默认在每次模型请求前先发送 `:stream 1`，等待其实际 READY，再发送原文。整个握手期间保持输入锁定，不会把设置命令的 READY 当作模型完成。
6. 原文发送瞬间显示“收到，正在发送…”，来源标签注明这是界面反馈。实际模型正文仍来自 UART，首个完整 UTF-8 字符到达后立即显示，不等整句或文本行换行。
7. 结束后导出记录，需要时导出原始 UART。实物是否发光仍由现场观察或录像确认，寄存器状态不等于已拍到发光。

多灯模式需要新的匹配 RTL/位流和以 `NX_LED_BANK=1` 构建的固件；仅替换本展示台不能使旧硬件获得四灯控制。主机只有实收 `T27 LED_BANK_CAPABILITIES` 后才开放多灯，串口桥也拒绝无该能力的多灯请求。模型推理期间直接控制按钮禁用；板端同步服务不会由主机界面自动抢占。若收到 `D27 HALTED` 或 `T25 TRAP`，本连接保留停止状态，后续孤立 READY 不会重新开放发送。

## 精确选择板上哪几颗灯

| 页面灯号 | 管脚 | 掩码位 | 解除接管后的原功能 |
| --- | --- | --- | --- |
| LED0 | A20 | bit 0 / 1 | 默认关闭 |
| LED2 | C19 | bit 2 / 4 | error 指示 |
| LED3 | E18 | bit 3 / 8 | heartbeat 指示 |
| LED5 | A18 | bit 5 / 32 | BIST 指示 |

四个灯的有效掩码为 `0x2d`（十进制 45）。支持全部 15 种非空子集，包含非连续组合。例如只选 LED2 和 LED5：

- 直接打开：`:ledm 36 36`。
- 直接关闭：`:ledm 36 0`。
- 让这两颗灯恢复原指示功能：`:ledauto 36`。
- 模型统一控制：`:actm 36 打开灯。`，保留原系统提示和 LED JSON 程序语义。
- 查询全部通道状态：`:ledm?`。

模型模式的目标来自明确勾选，并在完整请求期间锁定；**本版不宣称能够从自由文字中自动识别或校验灯号**。若想控制不同灯组分别开关，可分次勾选并发送。每次操作只作用于选中掩码，新硬件提供同时更新所选灯的寄存器接口。未知灯位、空目标或越出目标的状态值会整条拒绝。

回执中 `values` 是软件状态字，`owned` 表示哪些灯被当前通道接管。页面仅对已接管灯显示“接管 · 开/关”；未接管灯一律显示“自动指示”，不会把状态字 0 误写为实物熄灭。自动灯的瞬时亮灭仍由原逻辑决定，实物发光需要现场观察。解除 LED0 接管会恢复其默认关闭行为。

成功需要回执掩码与请求完全相符、已选灯接管/读回匹配；存在前一次有效状态时，还核对未选灯的接管位和软件状态没有改变。旧单灯回执不能代替多灯回执，错误/超时不能转为成功或自动直接控灯补救。

## 哪些等待发生了变化

- **真实灯控快路径**：原本折叠在调试区的 `:led 0/1/?` 已提升为独立模式，新四灯固件使用带目标掩码的直接接口。没有模型计算开销，结果以实际读回为准；不把它呈现为模型理解的成绩。
- **普通文字首字**：每次请求默认确认流式开启，避免之前设置 `:stream 0` 后等待完整生成才看到正文。取消“每次模型请求前确认开启流式”可回到原手动方式。
- **即时可感知反馈**：本地接收反馈、串口写入确认、板端收到、输入处理、生成、校验、准备执行均分开显示。无预填模型回答、假进度百分比或提前成功。
- **传输保持增量**：原有一字节唤醒串口读、条件变量长轮询和增量 UTF-8 预览已是及时路径，本版保留。`wait=20` 是无新字节时的最长等待；有字节立即唤醒，不是固定 20 秒刷新。

板端模型仍需完成推理。主机改动不能单独把模型本身的数十秒/数分钟计算降到毫秒。

## 延时口径

导出的灯控运行记录保存不可变的 `targetMask`，普通文字该字段为空。每个记录有 `requestSource`：`board_model`、`direct_uart` 或 `service_control`，并保留原始命令、字节、会话、回执、板端统计和来源。

| 字段 | 含义 |
| --- | --- |
| `latency.ui_feedback_ms` | 用户点击到本地反馈 DOM 更新；不计作模型首字 |
| `latency.board_received_ms` | 点击到实收可选 RECEIVED 消息；旧固件没有时留空 |
| `latency.first_uart_token_ms` | 点击到实收第一个 TOKEN 事件；可能尚无可见字符 |
| `latency.first_visible_receive_ms` | 点击到包含首个可见模型字符的浏览器接收块 |
| `latency.first_visible_dom_ms` | 点击到首个可见模型字符更新到页面 |
| `latency.first_visible_frame_ms` | 下一次浏览器 animation-frame 回调机会；不是光学屏幕测量 |
| `latency.action_receipt_ms` | 点击到完整 ACTION/LED 回执行到达；尚未含最终 READY |
| `latency.ready_ms` | 点击到实际 READY；断线不会填入这个字段 |
| `latency.disconnected_ms` | 中断结束时间，不能当作 READY |
| 板端 `first_token_ticks` | 模型内部首 token，保留原口径 |

上述主机相对延时都来自同一浏览器 `performance.now()`，包含该次点击触发的流式预设置等待。串口桥 `monotonic_ns` 原样保存，绝不与浏览器时钟直接相减。动作回执的到达与最终成功结论分开；成功仍要求完整正文、EOS、写次数、目标读回和最终协议校验。

## 回退与兼容

- 新主机可用于旧固件，保持原 LED0 通道；旧固件缺少 RECEIVED/PHASE 时仍按原 REQUEST、STREAM、METRICS、READY 工作。
- 本轮固件新增的阶段事件没有增加强制能力位。新主机支持可选 `received` / `phase` 能力声明，旧严格能力解析器不应接收未来未知的能力位。
- “直接控灯”无关键词识别，不把中文原文悄悄改写为直接命令；模型失败后也不自动走直接控制。
- 断线、超时或流式预设置失败不重发原文。超时继续被动接收，保留未完成状态；取消是否能恢复服务由板端决定。
- 回退主机可恢复上传包中的原 `code/host_console`，或先取消流式预设置选项。主机不写 FPGA、SD、Flash 或模型权重。

另将真实 `main.c` 的本地模拟执行产生的 4 组 UART 输出按 5 种分块方式解析，共 20 项命令/目标相关验证通过。可用 `node tests/test_bank_main_integration.mjs <包含 BANK_WIRE_FIXTURES.json 的目录>` 复验；这些夹具使用模拟 MMIO 和指定生成 ID，不是模型准确率或实板证据。

`tests/browser_smoke.py` 已随交互更新，保留给有 Playwright/Chromium 的环境继续检查。**本环境没有 Chromium；本轮未执行真实浏览器、Windows EXE、真实串口、模型或灯具测试**。原 v4 的 Windows 验收记录仅属历史，不能继承为本版已验收。

`static/binding.json` 只保留历史已验收板卡的绑定；本版主机文件摘要在 `HOST_MANIFEST.json`。新固件源码候选不等于已部署固件。T27 资格状态与历史物理证据由上层交付说明管理。
